The Path to Moksha

A Jain pilgrimage arcade platformer in Python and pygame-ce: four levels, a randomized item roulette, a monk who answers to knowledge rather than reflexes, and the timer as the only score. This is what the folder actually contains, how it fits together, and where the shipped build parts ways with the documents that describe it.

01 What this project is

You play a Shravak (boy) or Shravika (girl) making a pilgrimage that starts in a Toronto streetscape and ends on a mountain summit. Each level hides one Goal item inside a set of visually identical mystery boxes. You open boxes to find it, dodging fire, water and snakes on the way, and the clock is both your fuel and your score. A meditative Monk stands somewhere in each level; answer his question on Jain doctrine correctly and he marks the Goal box for you, converting knowledge directly into saved time. That is the whole thesis of the design, stated in the source notes as “Guidance over Gating.”

The repository is unusually well documented for a hobby game — there is a GDD, an architecture doc, a decision log, a developer reference, a 40 KB design-review transcript, and a reusable engine template. The code largely honours those documents, with a handful of real divergences catalogued in section 08.

03 Architecture

A single owner — Game in main.py — holds three long-lived managers and one scene registry. Every frame follows the same order: pump SDL events, update input, let the active scene consume events, update it, draw it onto a fixed 1920×1080 surface, then smoothscale that surface into whatever window the player has. Physics and UI layout therefore never see the real resolution, which is why the same jump arc works windowed and fullscreen.

04 Scene flow

Every screen is registered up front and switched by key. The one thing the navigation graph makes visible that no document states: in the two player-facing modes the run ends after Level 2. Levels 3 and 4 are built, populated and playable, but only developer mode walks past the “to be continued” gate into them — and the Victory screen, with its ranks, sits behind that gate.

05 Gameplay

The moment-to-moment loop is short and legible: move, jump, find a box, decide whether to open it. Everything the player can gain or lose is denominated in seconds, so the risk of an unknown box is always priced in the same currency as the reward.

Controls

One abstraction layer, three input devices, no separate code paths in the scenes. Move with arrows / A D / stick / D-pad / on-screen arrows. Jump with Space, Up, gamepad A, or the on-screen JUMP. Interact with Enter, E, gamepad X, or ACT. F3 toggles an FPS overlay; Esc backs out. Custom pad bindings live in data/controller_map.json and are validated against the connected device before being trusted.

Box roulette

Six boxes per level, shuffled and placed on random platforms with a 50-attempt safety search that keeps them clear of hazards, the Monk and each other. Opening one pauses the world and shows a pop-up; the effect only lands when you dismiss it.

The mix shifts by level. Level 1 is the harshest gamble — one Goal, two Support, three Distraction. Level 4 is the gentlest — one Goal, three Support, one no-effect, one Distraction.

Level 2 is the most designed level in the game. Finding the Akshat flips player.can_fly, which disables gravity entirely and switches to 8-way floating control, and appends a new platform at Rect(15,150,150,150) where the Bhagwan image sits. The goal text in level_goals.json swaps to match. It is the only level where the goal item changes how the character moves.

The Monk

One Monk per level, on a fixed ledge in Levels 1–2 and randomly placed on a hazard-free platform in 3–4. Walk into a 60×40 inflated zone and a “press UP” prompt appears; accepting opens a full-screen parchment with the question typed out character by character and two choices. Questions come from monk_questions.json (or the kids variant), four per level, and the session tracks which have been asked so a run never repeats one. A correct answer calls highlight_goal_box(), which pulses a green outline around the Goal box and the first unopened Support box. One attempt per level, right or wrong.

Per level, score is remaining_seconds × 10, banked once when the completion banner appears and accumulated into total_score. The Victory screen then computes its own number — max(500, 10000 − total_time×15 + 1500 × correct_monk_answers) — and overwrites final_score with it. Rank comes from total elapsed time alone: under 4 minutes is Moksha Margi, under 8 is Shravak, beyond that Bhakt. Profiles and a top-500 leaderboard persist to JSON, and a score is only recorded when it strictly beats the player's previous best.

06 Data and persistence

Content that changes often is externalized; level geometry is not. Platforms are hardcoded pygame.Rect lists in level_layouts.py, hand-tuned against the background art — some coordinates carry fractional values from a click-to-place workflow still present in the code. Box definitions are a Python dict in box_system.py. Questions and goal text are JSON. The template/schemas/ folder documents JSON formats for boxes, levels, dialogue and sprites that the engine does not yet read — forward work for reusing this as a generic engine.

07 Build and distribution

PyInstaller for both desktop targets, with separate spec files. GitHub Actions runs a portability test suite on Ubuntu, then builds the Windows .exe and the macOS .app, publishing on v* tags. The macOS script validates, ad-hoc signs (or Developer-ID signs when MACOS_CODESIGN_IDENTITY is set), and zips the bundle; notarization is wired but optional. The test suite is deliberately import-free — it parses source with ast and mocks sys.frozen — so it runs on a headless worker before pygame is installed. It is the only automated test in the project, and it checks packaging integrity rather than gameplay.

08 What the code does that the docs don't say

These are all verified against the source, not inferred. Ordered by how much they'd affect a player or a maintainer.

HighThe Monk's correct answer is always the first option

All 32 questions across both question files have "correct": 0, and the choices are never shuffled before display. A player who notices this gets a free Goal-box reveal every level, which removes the entire knowledge-versus-time trade the mechanic exists to create.

assets/monk_questions.json · assets/monk_questions_kids.json · monk_system.py (no shuffle of q["choices"])

HighTwo call sites crash if a negative starting level is set

A misplaced parenthesis turns the keyword argument into a second positional argument to abs(): abs(starting_level, input_mgr=self.input_mgr) raises TypeError. It sits on the developer level-skip branch, so a normal run never touches it — but the same shortcut in character_select.py works, which means the shortcut succeeds for a new profile and crashes for an existing one.

player_select_scene.py:332 · leaderboard_scene.py:151

MediumHazards don't reset the player — they charge 30 seconds

The GDD states that fire and water “cause the player to reset to the start of the level.” The implementation subtracts 30 seconds and freezes for 1 second, with a 2-second per-hazard cooldown. The docs and the build describe different games here, and the code's version is arguably the better one — a doc fix, not a code fix.

hazards.py:14–16 · level_scene.py:775–778 vs docs/GDD.md

MediumLevels 3 and 4 end the moment the Goal box opens

The README tells players to “locate the Goal Box and then reach the temple gate at the end of the level.” That is true only in Level 1. Level 2 substitutes the Bhagwan offering. Levels 3 and 4 fire level_complete directly from the box, so their long ascending layouts have no destination — whichever platform the Goal box happened to land on is the finish line.

level_scene.py:564–568

MediumLevel 2 has neither fire nor water

Both the GDD and the design review in Game Play v2.txt make “Water AND Fire in every level” a named correction principle. Level 2 ships with two patrolling snakes and nothing else; the snakes are behind a module-level ENABLE_LEVEL2_SNAKES test flag that is currently the level's only hazard source.

hazards.py:150–158

MediumMissing backgrounds render as hot pink

assets/images/backgrounds/ holds art for the title, Level 1 and Level 2 only. Levels 3 and 4 hit the AssetManager's deliberate fallback and draw a magenta rectangle behind the whole level. assets/fonts/ is empty too, so every scene silently uses the default pygame face despite the font-path machinery.

asset_manager.py:29–34

MediumTwo scoring systems, one field

Levels bank remaining_seconds × 10 into total_score, and _advance_level copies that into final_score and saves it to the profile. On reaching Victory, a second, unrelated formula recomputes final_score and saves again. A player who ends in kid mode after Level 2 and a player who finishes all four levels have scores on the same leaderboard that were computed different ways.

level_scene.py:1132–1140 · victory_scene.py:45–50

LowA level-design tool is live in the shipped gameplay path

Every mouse click during a level prints a ready-to-paste p.append(pygame.Rect(...)) line to stdout. Harmless in a windowed build, but it fires on the same clicks players use for the touch controls.

level_scene.py:330–337

LowFalling off the world is free

A player below y = LOGICAL_HEIGHT is teleported to y = 100 with zeroed velocity — dropped back in at the top of the screen at no cost. In levels built as vertical climbs, falling is faster than descending.

level_scene.py:161–163

LowAssetManager.get_image() can never return anything

load_image caches under a (path, scale) tuple; get_image looks up a bare path string. The lookup always misses and returns None. Nothing currently calls it, so it is dead rather than broken — but it is a trap for the next caller.

asset_manager.py:45–48

LowRepository hygiene

760 MB checkout carrying venv/, build/, dist/, Old/ asset folders and a backups/ directory of nine superseded modules. Twelve files are modified and uncommitted, including the built dist/PathToMoksha.exe.

09 If you want a shortlist

  • Shuffle the Monk's answers. One random.shuffle with a remapped correct index restores the mechanic the whole design is built around.
  • Decide what Levels 3 and 4 are. They are complete geometry with no backgrounds, no exit condition and no route from normal play. Either finish them or state in the docs that this build ends at Level 2.
  • Pick one scoring formula. Whichever it is, compute it in one place so the leaderboard compares like with like.
  • Reconcile the GDD with the build on hazards, on Level 2's missing fire and water, and on where each level actually ends.
  • Move platform layouts into the JSON schema the template folder already defines. It is the last thing keeping level design inside Python.
